# 加速 E3 阈值计算代码修改计划

> 适用对象：`step1_split_E3_thresholds_from_union_cache.py`（以下简称 E3）
> 配套改动：`infos/hpc_step1/create_jobs_kunshan.py`（作业生成器）
> 阶段：**仅代码修改计划，暂不实现**

## 1. 背景与目标

E3 从 E2b 合并后的 union station CF cache 计算三个 SSP 的稀疏低资源阈值。在昆山超算实测：

| tech | 服务器 | SSP 串行单核耗时 |
|---|---|---|
| wind | 昆山185 | ~3.6 小时 |
| solar | 昆山199 | ~1.5 小时 |

**慢的根因（两个独立瓶颈）**：

1. **单线程**：作业脚本 `#SBATCH -n 4`，但 E3 用 numpy/pandas 串行计算，且 Slurm 脚本里 `OMP/MKL/OPENBLAS_NUM_THREADS=1`，实际只用到 1 核（CPU 效率 ~23%，与 E2a probe 实测一致）。
2. **SSP 串行**：一个作业内顺序算 ssp126 → ssp245 → ssp585，三个 SSP 无并行。

**目标**：通过两层加速把 wind 从 ~3.6h 降到 ~15-20 分钟、solar 降到 ~10 分钟：
- **层一（SSP 间并行）**：E3 加 `--scenarios` 参数，每个作业只算 1 个 SSP，三个 SSP 分别提交作业并行。
- **层二（作业内多核）**：E3 加 `--n_jobs` 参数，chunk 计算用进程池并行；Slurm `-n` 与 `--n_jobs` 取同一个值，默认 **10 核**。

## 2. 现状与瓶颈

### 2.1 计算量（实测）

| SSP | wind 站数 | solar 站数 |
|---|---:|---:|
| ssp126 | 86642 | 77707 |
| ssp245 | 82795 | 36764 |
| ssp585 | 38460 | 4114 |
| 合计 | 207897 | 118585 |

实测单核速度：wind ~968 站/分、solar ~1311 站/分。

### 2.2 瓶颈定位

E3 计算核心是 `scripts/precompute_low_resource_thresholds.compute_threshold_block(cf_block, times, *, pct=5.0, window_steps=24)`，它对每个 128 站 chunk 做：

- 24 小时居中滚动平均（pandas rolling）
- 月-小时气候态 `clim(12, 24, station)`（12 月 × 24 小时分组的 nanmean）
- 距平 `anomaly = roll - clim[month, hour]`
- P5 阈值（nanpercentile）

该函数是**纯函数**（仅 numpy/pandas 计算，无文件 IO、无全局状态），输入 `cf_block (time, n_cell)` + `times`，输出 `(clim, threshold, valid_count)`。**天然适合并行**：不同 chunk 之间完全独立。

当前 E3 在 `run()` 内用串行 for 循环逐 chunk 调用，且一个作业内串行处理 3 个 SSP，两层都未并行。

## 3. 加速方案总览

| 方案 | wind | solar | 实现成本 |
|---|---|---|---|
| 现状（串行单核） | ~3.6 h | ~1.5 h | — |
| 仅拆 3 SSP 并行 | ~1.5 h | ~1.0 h | 低 |
| 仅多核（10 核） | ~25 min | ~12 min | 中 |
| **拆 3 SSP + 10 核（本方案）** | **~15-20 min** | **~10 min** | 中 |

两层加速相互独立、可叠加：拆 SSP 把 3 个 SSP 的墙钟时间折叠成最慢的那一个；多核再把每个 SSP 的计算时间按核数缩短。

## 4. 代码修改细节

### 4.1 E3：新增 `--scenarios` 参数（拆 SSP）

**目的**：让一个 E3 作业只处理指定 SSP，输出单个阈值文件，从而三个 SSP 可分别提交作业并行。

**改动点**（`step1_split_E3_thresholds_from_union_cache.py`）：

1. `build_parser()` 新增：
   ```python
   parser.add_argument(
       "--scenarios",
       default=",".join(SCENARIOS),   # 默认 "ssp126,ssp245,ssp585"，保持兼容
       help="只计算指定 SSP（逗号分隔），默认全部三个",
   )
   ```
2. `run()` 开头解析并校验：
   ```python
   selected = [s.strip() for s in args.scenarios.split(",") if s.strip()]
   unknown = [s for s in selected if s not in SCENARIOS]
   if unknown:
       raise ValueError(f"不支持的 scenario: {unknown}，可选: {SCENARIOS}")
   ```
3. 将 `for scenario, map_path in map_paths.items():` 改为只遍历 `selected`。
4. **输出存在性检查收紧**：原代码检查全部 3 个输出文件是否存在（`outputs = [_scenario_output(...) for scenario in SCENARIOS]`）。改为只检查 `selected` 对应的输出，避免单 SSP 作业因“别的 SSP 文件不存在”而误判。
5. 原子写出循环（`for tmp, output in zip(temp_outputs, outputs, ...)`）只覆盖 `selected` 的输出，不影响其他 SSP。

**兼容性**：默认值保持全部 3 个 SSP，旧调用方式行为不变；现有测试 `test_e3_writes_three_scenario_threshold_files` 不受影响。

### 4.2 E3：新增 `--n_jobs` 参数（作业内多核）

**目的**：把 chunk 级 `compute_threshold_block` 调用用进程池并行，单作业吃满多核。

**依赖选择**：用标准库 `concurrent.futures.ProcessPoolExecutor`，**不引入新依赖**（与项目此前对 `global_land_mask` 等可选包的谨慎态度一致；`joblib` 作为备选，若后续已引入可平滑替换）。

**改动点**：

1. `build_parser()` 新增：
   ```python
   parser.add_argument("--n_jobs", type=int, default=1,
                       help="chunk 级并行进程数，需 ≤ Slurm -n；默认 1（串行，兼容）")
   ```

2. 新增模块级 worker 函数（必须顶层定义以便 pickle）：
   ```python
   def _compute_chunk(cache_path, chunk_positions, times, pct, window_steps):
       """worker 内自开 cache 只读句柄、排序读 cf 切片、算阈值，返回 (clim, threshold, valid_count)。

       worker 自读 HDF5 是为了避免把每 chunk ~45MB 的 block 在进程间 pickle 传递。
       """
       with cf_low_resource.open_h5(cache_path, "r") as handle:
           order = np.argsort(chunk_positions, kind="stable")
           inv = np.empty(order.shape, dtype=np.int64)
           inv[order] = np.arange(order.size)
           block = handle["cf"][:, chunk_positions[order]].astype(np.float32)[:, inv]
       return full_precompute.compute_threshold_block(
           block, times, pct=pct, window_steps=window_steps
       )
   ```
   注：worker 内复用已修复的“排序读 h5py”逻辑（见 commit `ad26e25`）。

3. `run()` 中 chunk 循环改造（`--n_jobs == 1` 时走原串行路径，保持兼容与可调试）：
   ```python
   chunk_plan = [
       (c0, min(c0 + args.station_chunk, len(stations)), positions[c0:c1])
       for c0 in range(0, len(stations), args.station_chunk)
   ]
   if args.n_jobs <= 1:
       iterator = (_compute_chunk(str(cache_path), cp, times, 5.0, 24)
                   for _, _, cp in chunk_plan)
   else:
       from concurrent.futures import ProcessPoolExecutor
       with ProcessPoolExecutor(max_workers=args.n_jobs) as ex:
           # map 保序；chunksize 减少 IPC 次数
           n_tasks = len(chunk_plan)
           cs = max(1, n_tasks // (args.n_jobs * 8))
           iterator = list(ex.map(
               _compute_chunk,
               [str(cache_path)] * n_tasks,
               [cp for _, _, cp in chunk_plan],
               [times] * n_tasks,
               [5.0] * n_tasks,
               [24] * n_tasks,
               chunksize=cs,
           ))
   for (c0, c1, _), (clim, threshold, valid_count) in zip(chunk_plan, iterator):
       if not np.all(np.isfinite(threshold)): raise ValueError(...)
       if not np.all(valid_count > 0): raise ValueError(...)
       ds["clim"][:, :, c0:c1] = clim
       ds["threshold"][c0:c1] = threshold
       ds["valid_count"][c0:c1] = valid_count
       logger.info("[%s/%s] 已计算 station %d:%d", scenario, args.tech, c0, c1)
   ```

**关键设计点**：
- **worker 自读 HDF5**：`_compute_chunk` 内自己 `open_h5`，不继承父进程句柄（fork 后 h5py 句柄不安全）。多个 worker 并发只读同一 cache 文件，HDF5 只读模式并发安全。
- **`times` 共享**：`times` 是 DatetimeIndex（~87600 个），pickle 体量小，可重复传每个 task；`match`（`_match_from_cache` 结果）只在主进程算一次，用于 `create_sparse_output` 建文件元数据，不进 worker。
- **map 保序**：`ProcessPoolExecutor.map` 按输入顺序返回，保证 chunk 结果按 `c0` 顺序写回 `ds`。
- **`chunksize`**：减少 task 调度与 IPC 次数（wind 单 SSP ~677 chunk）。

### 4.3 生成器：新增 E3 并行作业脚本

**目的**：为每个 (tech, SSP) 组合生成独立 10 核作业脚本，输出到新目录，与旧 E3 作业脚本区分。

**改动点**（`infos/hpc_step1/create_jobs_kunshan.py`）：

1. 新增 CLI 参数：
   ```python
   parser.add_argument("--e3_parallel", action="store_true",
                       help="生成按 SSP 拆分的多核 E3 作业（默认 10 核）")
   parser.add_argument("--e3_kernel_num", type=int, default=10,
                       help="E3 并行作业核数，同时用于 Slurm -n 和 E3 --n_jobs")
   parser.add_argument("--e3_output_suffix", default="parallel",
                       help="E3 并行作业输出目录后缀，如 sparse_station_ERA5Land_2015-2024_parallel")
   ```
2. 新增函数 `run_e3_parallel(args, config, ...)`，为每个 SSP 生成：
   - 作业脚本：`job_step1_E3_{tech}_{scenario}.sh`（文件名带 SSP，与旧 `job_step1_E3_{tech}.sh` 区分）
   - SBATCH 头：`#SBATCH -n {e3_kernel_num}`（默认 10）、`--time` 沿用 `--e3-time`
   - 命令：
     ```bash
     python step1_split_E3_thresholds_from_union_cache.py \
       --union_station_cf_cache <merged_cache> \
       --union_stations_csv <union_csv> \
       --index_map_ssp126 <...> --index_map_ssp245 <...> --index_map_ssp585 <...> \
       --tech {tech} --baseline_years 2015-2024 \
       --scenarios {scenario} \
       --n_jobs {e3_kernel_num} \
       --output_dir {project}/outputs/low_resource_thresholds/sparse_station_ERA5Land_2015-2024_{e3_output_suffix}
     ```
     - **保存目录必须 ≠ 旧 E3 目录**：`--e3_output_suffix`（默认 `parallel`）拼到旧目录名后得到 `sparse_station_ERA5Land_2015-2024_parallel/`，与旧 E3 的 `sparse_station_ERA5Land_2015-2024/` 严格不同，确保新旧作业的输出文件互不覆盖、可同时运行。
3. 新增 submit 脚本 `submit_step1_E3_parallel_{tech}.sh`：依次 `sbatch --parsable` 该 tech 的 3 个 SSP 作业。
4. **不动**既有 `job_step1_E3_{tech}.sh`（单作业 3 SSP 串行版）的生成逻辑，保持兼容；`--e3_parallel` 是新增独立路径。

## 5. 新旧并存策略（与正在跑的旧 E3 不冲突）

> **硬性要求：新 E3 的保存目录必须与旧 E3 不一致。**
> 旧 E3 产出 `sparse_station_ERA5Land_2015-2024/`；新 E3 必须写入**不同目录**（默认 `sparse_station_ERA5Land_2015-2024_parallel/`），防止与旧 E3 的输出文件重复或互相覆盖。这是新旧作业能同时运行、互不影响的根本前提，下面所有维度的取值都服务于这一要求。

| 维度 | 旧 E3 | 新 E3（本方案） | 是否必须不同 |
|---|---|---|---|
| 作业脚本 | `job_step1_E3_{tech}.sh` | `job_step1_E3_{tech}_{ssp}.sh` | 是（防覆盖脚本） |
| **保存目录** | `sparse_station_ERA5Land_2015-2024/` | `sparse_station_ERA5Land_2015-2024_parallel/` | **是（防输出文件重复/覆盖）** |
| 读取 | 同一 merged cache（只读） | 同一 merged cache（只读） | 否（只读可共享） |
| SSP | 一作业算 3 个 | 一作业算 1 个 | — |
| 核数 | `-n 4` | `-n 10` | — |

- **读不冲突**：merged cache 为只读 HDF5，新旧作业并发读安全。
- **写不冲突**：输出目录不同，文件名按 SSP 区分。
- **队列限额**：新 E3 共 6 个作业（wind 3 + solar 3），分属两账号各 3 个；连同旧 E3 各 1 个，每账号在途 4 个，远低于 20 上限。
- **CPU 占用**：新 E3 每作业 10 核，峰值 wind 3×10 + solar 3×10 = 60 核，叠加旧 E3 8 核；需确认提交时段节点空闲（sinfo 有大量 mix/idle 节点，单节点 32/64 核可容纳 10 核作业）。
- **结果取舍**：新作业完成后，`..._parallel/` 目录下的 6 个阈值文件即为加速版结果；旧 E3 可任其跑完作对照，或手动 scancel。

## 6. 超算执行流程

1. **本地**：按本计划改 E3（`--scenarios`、`--n_jobs`、worker）+ 生成器（`--e3_parallel`）+ 补测试。
2. **本地**：`pytest tests/test_hpc_step1.py` 通过后 `git commit` → `git push`。
3. **超算 185 / 199**：`git pull` 到新 commit。
4. **超算**：运行生成器生成新 E3 脚本（示例）：
   ```bash
   python infos/hpc_step1/create_jobs_kunshan.py \
     --server scnet-kunshan-185 --e3_parallel --e3_kernel_num 10 --force
   ```
   产出 `job_step1_E3_wind_ssp126/ssp245/ssp585.sh` + `submit_step1_E3_parallel_wind.sh`（solar 同理，在 199 上 `--server scnet-kunshan-199`）。
5. **超算**：提交（示例）：
   ```bash
   cd jobs/step1_low_resource && bash submit_step1_E3_parallel_wind.sh   # 185
   cd jobs/step1_low_resource && bash submit_step1_E3_parallel_solar.sh  # 199
   ```
6. **监控**：新作业写 `..._parallel/`；用 `squeue`/`sacct` 跟踪 6 个作业；预计 15-20 分钟（wind）/ ~10 分钟（solar）完成。
7. **验收**：检查 `..._parallel/` 下 6 个 `.nc` 文件变量完整（clim/threshold/valid_count 有限）。

## 7. 验证标准

### 7.1 单元测试（`tests/test_hpc_step1.py` 新增）

1. **`--scenarios` 单 SSP 正确性**：用同一合成 cache 分别跑 `--scenarios ssp126` 和全量，断言单 SSP 产出的文件与全量对应 SSP 的 `clim`/`threshold`/`valid_count` 完全一致。
2. **`--n_jobs` 多核等价性**：同一输入分别用 `--n_jobs 1` 与 `--n_jobs 4`，断言输出数值完全一致（并行只改速度不改结果）。
3. **多核 + 无序 positions**：覆盖 4.2 的 worker 排序读路径，确保多核下仍正确处理无序 positions（回归 commit `ad26e25`）。
4. 现有 `test_e3_writes_three_scenario_threshold_files`、`test_e3_handles_unsorted_positions` 保持通过（默认行为不变）。

### 7.2 超算实测验收

- 6 个新作业全部 `COMPLETED`（exit 0）。
- `..._parallel/` 下 6 个文件变量齐全、`threshold` 有限、`valid_count > 0`。
- 与旧 E3（若跑完）同 SSP 输出数值一致（允许浮点 `allclose`），证明加速不改变结果。

## 8. 预期收益

- wind：~3.6 h → **~15-20 min**（拆 SSP 把墙钟折叠到 ssp126 的 ~89 min，再被 10 核压到 ~10 min，叠加 IO/IPC overhead 保守估 15-20 min）。
- solar：~1.5 h → **~10 min**。
- CPU 利用率：~23% → 接近满核（10 核作业）。
- 后续重跑成本大幅下降（step1 阈值计算不再是大头）。

## 9. 风险与注意事项

1. **HDF5 并发只读**：多 worker 同时 `open_h5(cache, "r")` 读同一文件，依赖 HDF5 ≥ 1.10 的并发只读支持（昆山 venv 的 netCDF4/h5py 满足）。若遇偶发锁错误，回退方案：主进程串行读 block、仅 `compute_threshold_block` 进池（block pickle 开销变大，但更稳）。
2. **进程池 + h5py fork**：worker 必须自己 `open_h5`，**不可**继承/复用父进程句柄（fork 后句柄失效）。worker 函数内开、函数内关。
3. **内存**：每 worker 读一个 chunk block ~45MB + 计算临时数组 ~数百 MB，10 worker 峰值约数 GB，节点内存（32/64 核节点 ~126/255 GB）充裕。
4. **`--n_jobs` 与 Slurm `-n` 一致**：生成器强制两者取同一 `--e3_kernel_num`；若手动跑需保证 `--n_jobs ≤ -n`，否则 worker 超过分配核数反而拖慢。
5. **IPC 开销**：`times`（~87600 长度 DatetimeIndex）每个 task 都 pickle；若成瓶颈，可改为传 `times` 的 numpy 数组或用 fork 继承（Linux 默认 fork 已继承父内存，`times` 可不显式传，但为显式安全仍传）。
6. **旧 E3 去留**：新作业提交后旧 E3 仍占资源；如确认新作业正常，可 scancel 旧 E3 释放核时。
